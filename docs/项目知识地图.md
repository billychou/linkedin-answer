## 2. Cloudflare 部署架构（项目技术核心）

### 2.1 当前实际部署方式：静态导出 + Pages Functions

这是理解整个项目最关键的一点：**项目当前不是 SSR，而是纯静态站 + 边缘 API**。

- `next.config.mjs:4` 配置 `output: "export"` → `pnpm build` 产出 `out/` 目录，全部是预渲染 HTML
- `out/` 部署到 Cloudflare Pages 作为静态资源托管
- `functions/` 目录被 Cloudflare Pages **自动识别**为边缘函数（Pages Functions），文件路径即 API 路由：`functions/api/me/index.ts` → `/api/me`

**为什么这么设计**：答案站的内容在构建时就确定了（答案写死在 .ts 文件里），不需要服务端运行时渲染；静态站零计算成本、全球边缘分发、天然抗流量峰值。用户系统等动态能力交给 Pages Functions 按需执行，按调用计费。

### 2.2 三份配置文件的分工

| 文件 | 作用 | 关键点 |
|---|---|---|
| `wrangler.toml` | 本地开发用（wrangler pages dev） | 声明了 D1 binding：`DB` → database `linkedin-answer`；注释明确警告不要加 `pages_build_output_dir`，避免锁死控制台配置 |
| `cloudflare.toml` | 参考文档性质，实际不生效 | 记录构建命令 `pnpm build`、输出 `out`、NODE_VERSION=20 |
| 控制台配置 | 生产环境的真正配置源 | D1 绑定、环境变量在 Cloudflare Dashboard 手动配置 |

### 2.3 部署方案的演进痕迹（四份文档对照）

项目经历了三代部署方案，文档都留着：

1. `DEPLOY_CLOUDFLARE.md`：最早方案，Pages Git 集成 + 已废弃的 `@cloudflare/next-on-pages`
2. `CLOUDFLARE_DEPLOYMENT.md` / `CLOUDFLARE_PAGES_SETUP.md`：迁移到 `@opennextjs/cloudflare` 适配器（支持完整 SSR），曾解决过 `worker.js not found` 问题
3. `CLOUDFLARE_PAGES_STATIC_DEPLOY.md`：最终落地的纯静态导出方案

**知识点**：Cloudflare 上跑 Next.js 有三条路线——
- **静态导出**（本项目现状）：`output: "export"`，只支持 SSG，无 SSR/middleware/API Routes
- **OpenNext 适配器**（`@opennextjs/cloudflare`）：完整 Next.js 运行时跑在 Workers 上，支持 SSR
- **next-on-pages**（已废弃）：早期官方方案

本项目装了 `@opennextjs/cloudflare` 但 `next.config.mjs` 没挂对应插件，实际走静态导出。这是一个"配置漂移"：依赖装了没用，若未来要恢复 SSR（比如让答案页在请求时动态读 D1），就要切回 OpenNext 路线。

### 2.4 部署命令

```bash

# 手动 CLI：
npx wrangler pages deploy out --project-name=linkedin-answer
# 本地全栈预览（含 Functions 和 D1 模拟）：
pnpm build && pnpm exec wrangler pages dev out
```

### 2.5 D1 数据库（`migrations/0001_users.sql`）

两张表，设计很讲究：

```sql
users          -- 业务用户表：内部 UUID 主键，email/name/avatar/bio/locale/timezone
               -- status/role + stripe_customer_id（为订阅制预留）
user_identities -- 第三方登录身份表：(provider, provider_subject) 复合主键，外键指向 users
```

**知识点**：
- D1 是 Cloudflare 的无服务器 SQLite，跑在 Workers 边缘，按读写计费，适合低中频写入场景
- "内部 UUID + 独立 identities 表"是多 OAuth 提供商的标准设计：同一用户先 Google 登录、后加 GitHub 登录，两条 identity 都指向同一个 user，见 `docs/user-system-design.md:46-53` 的设计决策
- `stripe_customer_id` 字段预埋在表里，说明数据建模时已考虑 Phase 2 订阅付费

## 3. 认证系统（SaaS 用户体系的标准范本）

### 3.1 Google OAuth 全流程

```
浏览器 /login 页
  ↓ Google Identity Services SDK（app/GoogleSignInScript.tsx:17-20）
  用户授权后 SDK 回调返回 credential（Google ID Token）
  ↓ lib/authClient.ts:32-48  POST /api/auth/login {credential}
Pages Function functions/api/auth/login.ts
  ↓ jose.createRemoteJWKSet 拉取 Google 公钥验证 ID Token（functions/_lib/auth.ts:33-35）
  ↓ 校验通过后 findOrCreateUserByIdentity 落库 D1（functions/_lib/db.ts:128-199）
  ↓ SignJWT 签发自己的会话 Token：HS256 + SESSION_SECRET，有效期 7 天
  ↓ Set-Cookie: session=xxx; HttpOnly; Secure（functions/_lib/auth.ts:121）
浏览器后续请求自动带 Cookie
```

**关键安全设计**：
- 会话 Token 存 **HttpOnly Cookie**，前端 JS 读不到，防 XSS 窃取；前端想知道"我是谁"只能调 `/api/auth/session`
- Google Token 只在登录瞬间验证一次，之后用自己的短期 JWT，不依赖 Google 服务可用性
- 用户合并逻辑：先查 identities 表 → 再按 email 归并已有账户 → 最后才新建（`functions/_lib/db.ts:128-199`），避免同人注册出多个账号

### 3.2 双层路由守卫

| 层 | 实现 | 作用 |
|---|---|---|
| 边缘层 | `functions/_middleware.ts`（Pages Functions 全局中间件） | 服务端拦截 `/chat`、`/settings`，无会话 302 → `/login?next=` |
| 前端层 | `lib/authClient.ts` 的 `fetchSession()` + `PROTECTED_PATHS` | 页面 mount 时二次校验，处理静态页无法做服务端拦截的情况 |

**知识点**：静态导出模式下 Next.js middleware 跑不了，所以守卫必须放在 Pages Functions 的 `_middleware.ts` 里——这是"静态站 + 边缘函数"架构特有的模式。`_` 前缀的文件/目录不会被映射成路由。

### 3.3 API 一览

| 端点 | 方法 | 功能 |
|---|---|---|
| `/api/auth/login` | POST | Google 登录，签发会话 Cookie |
| `/api/auth/dev-login` | POST | 开发环境假登录（`DEV_FAKE_LOGIN` 开关控制） |
| `/api/auth/logout` | POST | 清 Cookie |
| `/api/auth/session` | GET | 返回 `{user}` 或 `{user: null}` |
| `/api/me` | GET / PATCH | 读/改用户资料；PATCH 用 **zod** 校验 name/bio/avatar/locale/timezone（`functions/api/me/index.ts:50-91`） |
| `/api/hello` | GET | 健康检查 |

**待办**：`@upstash/ratelimit` 已安装但还没接入，设计文档计划给 `/api/auth/login` 和 `/api/me` PATCH 加限流（`docs/user-system-design.md:252`）——这是当前最明显的安全缺口。

## 4. 内容系统与渲染（答案站的 SEO 引擎）

### 4.1 路由与渲染策略

全静态导出，所有页面 SSG，`generateStaticParams` 在构建期穷举：

| 路由 | 生成逻辑 |
|---|---|
| `/games/[gameSlug]` 今日答案页 | 遍历 7 个游戏 slug；取 `getTodayAnswer()`：先精确匹配今天日期，未命中 fallback 到数组第一项（`lib/answers.ts:24-36`） |
| `/games/[gameSlug]/[date]` 历史答案页 | **统一的动态路由**，`generateStaticParams` 返回所有游戏 × 日期的组合；URL 与之前按游戏拆开的版本完全一致 |
| `/games/[gameSlug]/archives` | 归档列表 |
| `/games/[gameSlug]/how-to-play` | 玩法说明（内容来自 `data/games.ts` 的 description） |
| `/games/play/[gameId]` | 4 个内置小游戏（2048、记忆翻牌等），`data/miniGames.ts` 定义元数据，组件 `dynamic()` 懒加载 |

**知识点**：`[date]` 路由现已统一为 `app/games/[gameSlug]/[date]/page.tsx`，通过 `generateStaticParams` 返回所有游戏 × 日期的组合；新增游戏只需在 `data/games.ts` 和 `data/answers/` 添加数据，无需复制路由文件夹。

### 4.2 答案数据模型（`types/game.ts:10-18`）

```ts
GameAnswer {
  sequence   // 期号，如 "#817"，用于去重
  date       // "YYYY-MM-DD"
  answer     // string 或 string[]（crossclimb 是词梯数组）
  clues?     // 线索数组（pinpoint 用）
  clueHint?  // HTML 字符串，逐条线索的解析
  hints?     // 提示
  image?     // queens/tango/zip/patches 用图片展示答案
}
```

答案以**日期降序**存在 `data/answers/*.ts` 数组里，最新在头部。数据结构即内容数据库——没有真正的数据库，TS 文件就是存储，git 就是版本管理。

### 4.3 SEO 体系（流量站的生命线）

- **metadata**：`lib/metadata.ts:28-93` 的 `constructMetadata()` 统一生成 title/description/OG/Twitter Card/canonical
- **JSON-LD 结构化数据**：每个页面注入 `Game`、`FAQPage`、`BreadcrumbList`、`CollectionPage` 四种 schema（`components/games/StructuredData.tsx`）——直接面向 Google 富摘要
- **sitemap**：`app/sitemap.ts` 生成全站 URL，历史日期页标 `changeFrequency: 'never'`（内容不再变的页面告诉爬虫别重复抓，省爬取配额）
- **AdSense**：`app/GoogleAdsense.tsx` 经 `next/script` 异步注入（`layout.tsx:117`），`public/ads.txt` 声明 DIRECT 授权
- **OG 图**：`public/og.png` + `og.webp` 双格式

### 4.4 MDX 内容系统（博客与静态页）

- **博客 UI**：`app/blog/page.tsx` 列出全部文章，`app/blog/[slug]/page.tsx` 渲染单篇；数据来自 `lib/getBlogs.ts` 扫 `blogs/{locale}/`，gray-matter 解析 frontmatter，按 pin+date 排序，`visible !== 'published'` 的过滤掉
- **多语言内容**：en/zh/ja 各 10 篇原创攻略，标题、描述、标签、正文均已翻译，URL 方案为 `/blog${post.slug}`（与 sitemap 一致）
- **静态页**：`content/{about,privacy-policy,terms-of-service}/{en,zh,ja}.mdx`，服务端 RSC 渲染
- **自定义组件**：`MDXComponents.tsx` 提供 Aside / Callout / Card + 带锚点的标题、表格、代码块样式

### 4.5 国际化

- `i18n/routing.ts`：en/zh/ja，`localePrefix: 'as-needed'`（默认英文不带前缀，URL 更短利于 SEO）
- 无 Next.js middleware，靠 next-intl 的 `createNavigation` 包装器做切换（静态导出下 middleware 不可用）
- `LocaleSwitcher.tsx`：`router.replace` 带 `{locale}` 参数原地切语言
- **局限**：i18n 只覆盖 UI 文案；答案内容硬编码英文。博客已实现 en/zh/ja 三语言版本，答案做本地化需要数据管道支持多语言 clueHint

## 5. 数据管道（内容供给的自动化）

### 5.1 七个 Python 抓取脚本（`data/update/`）

| 脚本 | 数据源 | 产物特点 |
|---|---|---|
| `update_pinpoint.py` | pinpointanswer.today | 文本答案 + clues + AI clueHint 解析 |
| `update_queens.py` | linkedinpinpointanswer.today | 皇后坐标文本答案 + AI clueHint |
| `update_tango.py` / `update_zip.py` | 同上对应页面 | ☀️🌙 网格行 / 路径文本答案 + AI clueHint |
| `update_patches.py` | 同上 | 答案图片 URL + 描述文本 + AI clueHint |
| `update_crossclimb.py` | 同上 | 词梯文本答案 + clues + AI clueHint |
| `update_mini_sudoku.py` | 同上 | 6×6 解题网格 + AI clueHint |

共同流程：requests 抓取（RSC 载荷）→ 提取内嵌 JSON → 按 sequence 去重 → 新条目插入数组头部 → 重写 .ts 文件。所有脚本共用 `ai_lib.py`：配置 `DASHSCOPE_API_KEY` 时用 qwen 按期生成 clueHint 解析（HTML 白名单净化 + TS 模板字符串转义），未配置或调用失败时降级为确定性模板，不影响答案主体。

**知识点与风险**：
- 数据源是第三方答案站，本质是二次分发；数据源改版/关闭则管道断裂，由 `answer-freshness.yml` 哨兵与各更新 workflow 的告警 issue 监控
- 这是"抓数据 + AI 增值加工"的典型内容管道模式；历史归档条目（约 600 期）多数没有 clueHint 解析，补齐历史解析需在配置 API key 后定向重跑补抓
- `scripts/update-pinpoint-data.ts` 是已被 Python 版取代的旧实现，可清理

### 5.2 站点级自动更新（`scripts/auto-update.sh`）

cron 定时（`cron-task.md`：每周一凌晨 3 点）→ git fetch 比对本地/远程 → 有更新则 pull + pnpm install + build 验证 → 构建失败 `git reset --hard` 回滚。

**注意区分两条更新链**：这条脚本更新的是"代码仓库"，不是答案数据。答案更新由 GitHub Actions 驱动：`update-answer-reusable.yml` 复用流程 + 7 个游戏的每日调度（UTC 8:30–9:00 各错开 5 分钟，12:30/13:00 兜底重跑），成功自动提交、失败开告警 issue（`data-alert` 标签，成功即自动关闭）。

## 6. 前端工程要点

- **Server/Client 组件边界**：答案展示区 `AnswerReveal`、`CluesDisplay`、`ArchivesList`、`FAQ`、`TodayPinpoint` 是 `"use client"`（需要交互/状态），其余静态部分是服务端组件——SSG 下 client 组件的逻辑在浏览器水合后执行
- **clueHint 渲染**：HTML 字符串经 `dangerouslySetInnerHTML` 渲染——有 clues 的游戏在 `CluesDisplay` 内，无 clues 的游戏（Queens/Tango/Zip/Patches/Mini Sudoku）在 `AnswerDisplay` 的 "How to solve it" 块（置于揭晓答案之后）。数据源是自产脚本生成的，风险可控，但这是 XSS 敏感点，若未来开放用户投稿内容必须加净化
- **Zustand userStore**（`stores/`）：登录成功后存用户信息，避免每个组件重复调 session 接口
- **日志**：边缘函数使用 `console` + Cloudflare Workers Observability；Node 环境（构建/脚本）无持久文件系统需求，已移除 winston 依赖

## 8. SaaS 开发知识地图（Cloudflare 生态版）

把本项目的实践抽象成可迁移的 SaaS 技能树，标注项目内的学习样本：

### 8.1 基础设施层
- **边缘计算模型**：Workers/Pages Functions 的 isolate 运行时（冷启动毫秒级、无 Node 完整 API、无常驻进程）→ 样本：`functions/` 全部接口
- **D1 数据层**：SQLite 语义、migration 管理、binding 注入、读写计费模型 → 样本：`migrations/0001_users.sql`、`functions/_lib/db.ts`
- **静态优先架构**：能静态的全部静态，动态能力下沉到边缘函数 → 样本：`output: "export"` + `functions/` 混合模式
- **配置管理**：wrangler.toml（本地）vs Dashboard（生产）的双轨配置 → 样本：`wrangler.toml` 的注释警告

### 8.2 用户体系层
- **第三方 OAuth 集成**：SDK 引入 → Token 验证（JWKS）→ 会话自管 → 样本：完整 Google 登录链
- **会话设计**：JWT + HttpOnly Cookie vs localStorage 的取舍 → 样本：`functions/_lib/auth.ts`
- **多身份合并建模**：user/identity 分表 → 样本：D1 表结构
- **输入校验**：zod schema 校验 API 入参 → 样本：`functions/api/me/index.ts`
- **路由守卫分层**：边缘中间件 + 前端校验双保险 → 样本：`_middleware.ts` + `lib/authClient.ts`

### 8.3 增长与变现层
